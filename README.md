# C++ BigInt 高精度大整数运算库

> 👨‍🎓 **写在前面 (Background & Version)**：
> 这是我在大一（Freshman Year）完成的一份 C++ 面向对象课程设计（Course Project）。
> 
> 这个项目其实经历了一次架构重构：最开始我完成了一个只支持正整数的无符号版本。后来在加入减法并引入负数时，我意识到原有的架构处理正负号会极其混乱。因此我决定重构，采用**“符号与绝对值分离（Sign-Magnitude）”**的设计模式重写了底层逻辑。为了区分，保留了 `pro`（升级版）的命名。
> 
> 作为一个刚接触编程不久的新手，这份代码可能显得比较冗长，没有用到什么高深的现代 C++ 特性（如移动语义）。但我尽力用最底层的逻辑、最直观的方式，把每一个边界条件、每一处内存分配都交代清楚。欢迎各位大佬指正！

## ✨ 项目功能 (Features)
* **基础运算**：实现了任意长度带符号整数的加法（`+`）、减法（`-`）、乘法（`*`）。
* **比较运算**：重载了 `==`, `!=`, `<`, `>`, `<=`, `>=`。
* **流操作**：重载了 `<<`，支持直接 `cout << a` 输出。
* **内存管理**：严格遵循 C++ **Rule of Three**（手写了析构、深拷贝构造、赋值重载），杜绝了内存泄漏和双重释放。
* **工程化**：附带 `Makefile`，支持 `make` 一键编译，代码通过 `g++ -Wall` 严格编译，**无任何 Warning**。

## 🛑 设计约束与技术挑战 (Design Constraints & Challenges)
本项目并非使用现代 C++ 的快捷写法，而是遵循了极其严苛的底层约束。这些约束虽然增加了实现难度，但也极大地锻炼了底层代码能力：

1. **禁用 STL 容器，强制手搓 C 风格指针（`char*`）**
   * **挑战**：这意味着无法依赖 `std::string` 自动管理内存。所有的动态内存分配、深浅拷贝、以及内存泄漏的防范，都必须从零手写，并时刻警惕越界问题。
2. **强制“大端序”存储（人类可读顺序）**
   * **挑战**：算法竞赛中通常采用小端序（逆序存储）以方便进位和扩容。而本项目强制要求高位在左。
   * **技术亮点**：为了应对这一挑战，我没有采用“补零对齐”这种空间复杂度极高的笨办法，而是**采用了双指针（`i` 和 `j`）从后向前遍历**，并结合 `borrow` 标志位，直接在原数组上完成了复杂的借位与去前导零逻辑。这极大地考验了对数组边界和内存偏移的掌控力。

## 🔍 架构设计差异说明 (Architecture Difference)
由于在开发时错过了群里提供的 `prog6.h` 参考模板，我独立设计了一套负数的表示方法。在完成代码后，我将自己的设计与参考模板进行了对比，记录如下：

* **我的方案（状态位组合）**：采用 `bool isNeg` 和 `bool isZero` 两个布尔变量。在逻辑上，两个 `bool` 各占 1 字节，看似比 `enum` 更省空间。但考虑到类内部 `char* s` 和 `size_t len` 的对齐机制（Padding），整体对象大小依然会被对齐到相同的字节数。
* **参考模板方案（枚举 `enum Sign`）**：使用 `-1, 0, 1` 来表示负、零、正。这种设计的精妙之处在于，它在物理层面规避了“既是负数又是零”的非法状态，且直接利用整型的比较特性（如 `sign > other.sign`）极大地简化了符号判断。

**性能反思**：在 CPU 指令层面，`bool` 比较和 `enum` 比较的耗时几乎没有区别（均为单条指令）。不过从代码健壮性和可维护性来看，模板给出的枚举状态机无疑是更优雅的设计。这次“错打错着”的独立设计，让我深刻理解了状态机与内存对齐的底层博弈。

仓库中的 `main.C` 是课程提供的标准测试样例。该样例覆盖了超大数、跨量级加减、正负号交替等极端边界情况。我保留了这份测试代码，以证明本 `BigInt` 库在应对极端测试数据时的健壮性。直接运行 `make` 即可看到结果。

## ⚠️ 已知局限与“为什么没做” (Known Limitations & Why)

为了工程的逻辑完整性，我并没有实现所有的高精度功能，请理解大一新生的头发存量：

* **关于除法（Division）**：
  本次作业没有实现大数除法。大数除法（长除法）涉及极为复杂的“不断试商、回退、再乘、再减”的回溯逻辑，且除法会导致小数产生。考虑到本次作业的核心考察点是**内存管理**和**基础运算符重载**，如果强行用 `char*` 手搓大数除法，容易掩盖掉对底层的练习。未来如果时间允许，我会学习并补充 `absDiv` 逻辑。

* **关于类型转换（Type Conversion）**：
  目前仅实现了从常规整型（`int`）到 `BigInt` 的构造（主要是为了兼容测试用例）。
  **没有支持 `long long`，也没有提供反向的 `to_int()` 接口。**
  原因很简单：超大型整数本身就只有作为字符串存在才有意义。如果传入或转换为超出范围的类型，极易发生溢出引发未定义行为（UB）。我觉得让一个高精度库提供这种“高危且无意义”的接口是不安全的，因此只保留了最基础且安全的 `int` 转换，超大数请直接使用字符串构造。
